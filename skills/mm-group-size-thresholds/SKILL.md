# 群体规模阈值（group size thresholds）

## R — 原文 (Reading)

> 如果你的群体只有几个人（例如直系亲属或小型公司），那么每个人都可以参与最重要的决策，了解与群体有关的所有内容。但如果人数达到10到15，这个简单的体系就会崩溃。
>
> — 《思维模型》, 第8章 > 携手共进

---

## I — 方法论骨架 (Interpretation)

组织规模每跨过一个量级，**原来那套运转方式就会失效，必须换架构**：

- **几个人**：人人参与最重要决策，人人了解全局。无正式结构。
- **10~15 人**：上述体系崩溃，需要小群体、独立项目等架构。
- **30~50 人**：需要团队划分与正式管理。
- **150 人**：需要传统公司架构。

**为什么成立**：维持"人人知情、人人参与"所需的沟通链路随人数平方增长，而每个个体的认知带宽是常数。因此崩溃不是管理失败，而是**结构性必然**——在某个点之后，全连通的协作方式在物理上不可维持。

**关键判据有两个，互相独立**：

1. **绝对规模阈值**：当前人数落在哪一档，就该用哪一档的架构。用 5 人的方式管 40 人，或用 150 人的方式管 12 人，都是错配。
2. **扩张速度判据**：**若一年内组织规模扩大超过一半，超速发展会带来大麻烦**——因为太多未融入组织文化的新人会冲淡文化。

第二条尤其容易被忽略：它意味着**危险不只来自绝对值，也来自增长率**。一年从 60 人涨到 150 人的伤害，比稳定在 150 人要大。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队从几人涨到十几人，创始人发现"什么事都得我自己拍板"，或反过来"什么事都定不下来"。
2. 组织在 30~50 人区间，还在靠口头同步与非正式协调，开始频繁漏球。
3. 拿到融资或大单，计划在一年内把团队翻倍或扩到两三倍。
4. 管理者困惑"是不是该设一层经理了"，担心加层级会变官僚。
5. 公司已经一百多人，还在用创业期的扁平方式运作，决策堵塞在少数人身上。
6. 快速扩张后老员工抱怨"公司变了"，用户在找原因。

### 语言信号 (用户的话里出现这些就应激活)

- "人一多就管不过来了"
- "是不是该设经理/分组了"
- "我们打算一年内把团队翻一倍"
- "决策越来越慢，都卡在我这儿"
- "新人多了以后老员工说氛围不对了"
- "扁平化管理还适用吗"
- "when do we need managers / scaling too fast / adding layers"

### 与相邻 skill 的区分

- 与 `mm-dunbar-s-number` 的区别: 邓巴数（约 150）给出的是**人类能维持稳定社会关系的认知上限**，是一个生物学/人类学常数，解释"为什么是 150"；本 skill 是一整套**组织架构的行动阶梯**（10~15 / 30~50 / 150 各该做什么）。前者解释机制，后者给出动作，150 是两者的交汇点。
- 与 `mm-hypergrowth-dilutes-culture` 的区别: 超速增长稀释文化是**一条独立的判据**（一年内扩大过半就有麻烦），本 skill 把它作为第二条判据纳入；前者专注文化稀释的后果与应对，本 skill 覆盖更广的架构问题。
- 与 `mm-the-mythical-man-month` 的区别: 人月神话讲的是**项目工期与人力不可互换**（加人未必加快）；本 skill 讲的是**组织规模与协作架构的匹配**。前者是项目层面的投入产出误区，后者是组织层面的结构转型。
- 与 `mm-culture-eats-strategy-for-breakfast` 的区别: 那句名言讲文化的优先性；本 skill 中文化是作为"规模扩张的风险点"出现的（新人冲淡文化），侧重不同。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **确认当前人数与 12 个月前的人数**
   - 完成标准: 拿到两个数字，算出绝对规模档位与年增长率。
   - 判停条件: 若问题其实只是单个项目排期或人力估算，转 `mm-the-mythical-man-month`。
2. **先跑扩张速度判据（优先级更高）**
   - 完成标准: 明确判断"过去/未来一年是否扩大超过一半"。若是，立即把文化稀释列为主要风险，并给出减速或加强文化融入的具体措施。
3. **对照绝对阈值定位当前档位**
   - 完成标准: 判定落在 几个人 / 10~15 / 30~50 / 150 哪一档，并说明该档位**必需的架构要素**（小群体与独立项目 / 团队与正式管理 / 传统公司架构）。
4. **列出"上一档的遗留做法"清单**
   - 完成标准: 找出至少 2-3 个已经失效但仍在沿用的做法（如全员参与所有决策、靠口头同步、无书面目标），逐条给出替代方案。
5. **给出分阶段的转型顺序**
   - 完成标准: 按"先拆小群体/独立项目 → 再设正式管理与团队 → 最后上公司级架构"的顺序给出可执行动作，并明确**不要跳级**（12 人不要直接上公司级流程）。每项动作标注触发它的具体症状。

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 只是单个项目的人手与工期估算问题——用人月神话。
- 想了解 150 这个数字的认知科学依据——用邓巴数。
- 组织规模稳定、问题出在战略或产品方向——换架构解决不了方向错误。
- 人数没变但协作变差——可能是流程或人的问题，不是规模阈值问题。

### 容易误用的地方

- 书中明示：这些阈值是**经验性转折点**，不是精确临界值。不要理解成"第 15 个人入职那天必须重组"。
- 书中明示：扩张过快的风险**特指"新人尚未完全融入组织文化"**，不是笼统的"扩张有害"。
- （推导, 非书中明示）提前套用上一档的架构。在 12 人时照搬 150 人的流程会扼杀效率——架构要匹配规模，不是越正式越好。
- （推导, 非书中明示）只盯绝对人数、忽略增长率。一年内扩大过半带来的文化稀释，可能比跨过某个阈值更致命。
- （推导, 非书中明示）把架构调整当成一次性事件。跨越阈值后新架构本身也需要时间稳定，频繁重组会叠加伤害。

### 容易混淆的邻近模型

- **邓巴数（Dunbar's number）**: 解释 150 这个上限的来由；本 skill 是把阈值转成架构动作。
- **人月神话（The Mythical Man-Month）**: 项目层的人力误区；本 skill 是组织层的结构转型。
