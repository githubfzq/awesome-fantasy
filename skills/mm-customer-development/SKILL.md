# 客户开发（customer development）

## R — 原文 (Reading)

> 客户开发的目标是通过对客户进行快速试验，运用科学方法……找出可持续的商业模式。你要与客户建立一个快速反馈循环，以便尽可能多地了解他们的需求
>
> — 《思维模型》, 第9章 > 缺少执行的愿景不过是幻想

---

## I — 方法论骨架 (Interpretation)

这个模型由史蒂夫·布兰克提出，它把"做产品"的顺序倒过来了：不是先闭门把东西做完、再想怎么卖，而是**先去把真实需求问出来**。

它的核心动作是建立一个**快速反馈循环**：不断向真实客户提出假设、得到反馈、修正假设，直到形成一套可以重复的获取与留存流程。书名里的"科学方法"不是修辞——它要求假说可以被推翻，而不是被印证。

为什么这样做更划算？因为它给创意**去风险化**：在办公室里推演三个月、投入后再发现方向错了，代价极高，而**直接与客户交谈比在办公室推演廉价得多**。同样花一天，去外面聊五个潜在客户得到的信息，远多于在工位上想一整天。

具体可以怎么做？书里点了几类：焦点小组、问卷调查、访谈。但所有方法有一个前提——**先弄清你的"客户"到底是谁**。这一点看起来理所当然，实际最常被跳过：很多人做了一堆访谈，访的全是根本不会付钱的人。

这个模型的践行者布兰克有一句被引用到烂但依然准确的话："**在办公室里找不到真知灼见，所以赶紧滚去外面吧！**"（Get out of the building.）

判据一句话：**你上一次和真实客户（会掏钱的人）说话，是什么时候？**

（提醒见边界部分）访谈本身也有陷阱：如果客户上来就指定一个具体方案，你很可能拿到的是一个解决方案而不是他的真实问题——那是马斯洛之锤在起作用，需要用 `mm-jobs-to-be-done` 挖到下面的任务。

---

## A1 — 书中的应用 (Past Application)

### 案例: 布兰克的"滚出去"
- **问题**: 创业团队在要不要做某个功能、某个方向上反复争论，因为谁也拿不出证据，只能比谁说得更响。
- **方法论的使用**: 布兰克的回答不是让团队继续辩论，而是让他们**离开办公室**——直接去向客户提出假设、马上得到反馈。他的名言是："在办公室里找不到真知灼见，所以赶紧滚去外面吧！"背后是一个很硬的效率判断：内部推演的成本高、信息量少、还带着已有偏见；一次真实的客户对话会以极低成本提供可能推翻整个构想的信息。
- **结论**: 作者引这句话是为了给客户开发定调——它是一个**速度优先**的动作，关键词是"快速试验"和"快速反馈"。目的不是做一份漂亮的调研报告，而是**尽快知道自己在不在错误的路上**。这也是为什么它被摆在产品/市场匹配之前：它是通往匹配的手段。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **团队在会议室里为一个没人能验证的问题吵了很久**: 需要立刻把争论转成可执行的外部验证动作。
2. **准备投入大量资源开发某个功能/产品之前**: 需要先用低成本把关键假设问出来。
3. **产品做完了但没人用、不确定原因**: 需要回到客户那里，而不是继续闷头改进。
4. **有大公司/投资人要求看"市场验证"**: 需要设计一组能产出可信证据的客户反馈循环。

### 语言信号 (用户的话里出现这些就应激活)

- "我们内部讨论了很久，谁也说服不了谁"
- "要不先做个市场调研/问卷？"
- "这个功能用户到底要不要？"
- "我一直没搞清楚谁会为这个付钱"
- "再开发下去之前要不要先问一下用户"
- "我们是不是应该多跟用户聊聊"
- "We should talk to customers first." / "Let's do some user interviews." / "Nobody wants what we built."

### 与相邻 skill 的区分

- 与 `mm-jobs-to-be-done` 的区别: 客户开发是**整套流程**（怎么建立与客户之间的快速反馈循环），待办任务是访谈中**问什么**的核心问题（客户实际雇你的产品去完成什么任务）。前者管方法与节奏，后者管内容与判据。
- 与 `mm-product` 的区别: 客户开发是**过程**，产品/市场匹配是这个过程想要到达的**状态**。并且在位置上，客户开发在前，匹配在后——书中转型的定义就是"做了大量客户开发之后仍无法达成匹配"。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先定位"客户"到底是谁**
   - 完成标准: 明确区分三类人——掏钱的人、使用的人、影响决策的人，并指出本轮访谈真正要找的是其中的哪一类。三者不一致时必须挑出付费方作为主对象。
   - 判停条件: 若用户说不出任何一类具体的人（只有"所有人都能用"），停止设计访谈，先做人群切分。
2. **把正在争论的东西写成可推翻的假设**
   - 完成标准: 输出 3-5 条形如"我们认为客户在 X 场景下会愿意为 Y 付 Z 元"的陈述，每条标明"若答错，我们会改变什么"。无法指明改变动作的假设应删掉。
3. **选择最便宜、最快的验证手段**
   - 完成标准: 按成本从低到高排序选定：访谈 < 问卷 < 焦点小组 < 假门测试 < 原型 < 实物。优先选能在几天内得到结果的一种，而不是信息量最大但耗时最长的一种。这是"快速反馈循环"的本意。
4. **设计访谈提纲时必须问"任务"而非"方案"**
   - 完成标准: 提纲里每条问题都在问客户想达成什么、现在怎么做的、上次遇到这问题是什么时候，而不是"你觉得我们这个 XX 功能好不好"。书里明确警告客户会把关注点放在特定解决方案上（马斯洛之锤），需要引导对方先用通俗语言解释想达到的目标。
5. **执行并记录，然后立即修正**
   - 完成标准: 得到不少于 5 次的有效接触记录，每条记录包含：原话引用、属于支持还是推翻某条假设。据此明确标注每条假设被验证 / 被推翻 / 仍未知。
6. **判断下一步：继续试验、加码、还是转介转型**
   - 完成标准: 给出明确结论——多数假设被验证 → 进入产品/市场匹配的加码阶段；被推翻 → 修正假设后再循环一轮；经过多轮仍无法收敛 → 明确转介给 `mm-pivot` 讨论转型，并要求带上客户类型的测算结果。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **需求已经清楚且已验证，只差执行**: 继续访谈会变成拖延的借口（"我们还在做用户研究"）。
- **需要的是统计显著性的定量结论**: 访谈和焦点小组样本小、偏差大，此时应该做 A/B 测试或随机对照实验，而不是客户开发。
- **涉及用户无法自陈的需求**（全新品类、底层技术）: 客户不知道自己想要从没见过的东西，此时访谈的价值有限。

### 书中警告的失败模式 / 容易误用的地方

- **书中明示**: 需警惕**客户把关注点放在特定解决方案而非真正要解决的问题上**（马斯洛之锤）。这是客户开发最隐蔽的失败模式——客户很真诚地告诉你他想要什么，但他说的是方案不是问题。
- **书中明示（相关提醒）**: 劳伦的经验是**请客户先用通俗语言解释想达到的目标**——这是绕开上述陷阱的具体手法。
- （推导, 非书中明示）**访谈了不会掏钱的人**: 最常见也最致命。朋友、同事、同行开发者的反馈往往热烈但无购买意图，会让团队误判。
- （推导, 非书中明示）**把循环做慢了**: 布兰克强调的是"快速"。做一份耗时六周、样本 200 人的问卷来满足内部论证需要，已经背离了这个模型的核心——它要的是尽快排除错误方向。
- （推导, 非书中明示）**只问满意度、不问行为**: 客户对"你喜不喜欢"的回答高度受礼貌偏差影响；要问"上一次你遇到这事是什么时候、你当时做了什么"。

### 容易混淆的邻近模型

- **待办任务（jobs-to-be-done）**: 它是客户开发过程中最该问的那个核心问题；缺了它，客户开发很容易退化成满意度调研。
- **科学方法（scientific-method）**: 客户开发就是科学方法在商业发现上的应用版本，两者共享"假设—检验—修正"的结构，但客户开发额外强调"速度"和"离开办公室"。
