# 邓巴数（Dunbar's number）

## R — 原文 (Reading)

> 想一想邓巴数（Dunbar's number）——150。这个数字得名于人类学家罗宾·邓巴（Robin Dunbar），是维持稳定、团结的社交群体的人数上限。
>
> — 《思维模型》, 第8章 > 携手共进

---

## I — 方法论骨架 (Interpretation)

150 是人类靠"人与人之间直接认识"能维持的群体上限。它的机制很朴素：**稳定团结依赖每个人大致知道别人是谁、在干什么、该怎么跟他打交道。**

在 150 人以下，这件事靠自然接触就能完成——你见过、聊过、听人提起过，就能在脑子里维持一张关系图。超过 150，这张图装不下了：你记不住每个人，也就无法靠"大家都认识大家"来协调行为。

为什么这会导致**突变**而不是渐变？因为协作方式有两套。小群体靠**隐性共识**运转——谁负责什么、遇到事找谁、什么算越界，都靠日常接触自然形成，不需要写下来。这套方式极高效，但它的载体是人的记忆力，而记忆力有硬上限。一旦越过上限，隐性共识开始出现空洞，而**没人知道空洞在哪**：A 以为 B 在处理，B 以为那是 C 的活。于是流程不是"逐渐变差"，而是"某天突然失效"。

关键判据是书中那句：**人数达到邓巴数之前管用的流程，超过之后会突然失效。** 所以这本质上是一个**前瞻性规划模型**，不是事后诊断模型——它真正的价值在于提前。

书中还指出同一概念可扩展到更小的阈值（10~15 与 30~50），即群体规模每跨过一档，协作机制就要换一次。

---

## A1 — 书中的应用 (Past Application)

### 案例: 书中未给具体公司案例
书中未给具体案例，仅给出定义与机制。作者在这里的用法是：**把它当作领导者要做的前瞻规划动作**——在组织规模逼近阈值之前，就预见到"原本管用的流程会突然失效"，并提前规划一个"调整适应期"（更严格的政策与程序、明确的跨部门互动流程），而不是等失灵之后再手忙脚乱地补架构。

---

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **公司/部门/社群正在快速扩张，接近或刚跨过 150 人（或 30~50 人）**: 需要预判哪些隐性共识即将失效，提前换成显性架构。
2. **"以前一句话就能搞定的事，现在要开三个会"**: 组织变大后协作成本陡增，需要按阈值定位原因并给出对应的机制替换方案。
3. **跨部门协作频繁掉球、互相以为对方在做**: 典型的隐性共识空洞，需要引入明确的责任人与交互流程。
4. **规划组织架构、制定年度人员编制时**: 需要按人数档位预设不同的管理机制，而不是等出问题再救火。

### 语言信号 (用户的话里出现这些就应激活)

- "公司从 80 人涨到 200 人了，感觉管理方式完全不适用了"
- "人多了反而效率更低了"
- "我现在认不全团队里的人了"
- "跨部门推个事特别难，谁都觉得不是自己的活"
- "小团队那一套现在不管用了"
- "我们要不要开始写流程了？"
- "We're hitting Dunbar's number." / "Things broke once we passed 150 people."

### 与相邻 skill 的区分

- 与 `mm-group-size-thresholds` 的区别: 群体规模阈值是**整套档位**（10~15 / 30~50 / 150），讲每一档该换什么机制；邓巴数是其中最著名、也是最终的那个**上限值 150**，讲"人直接维系关系的硬顶"。讨论具体档位切换时用前者，讨论最终上限与突变时用后者。
- 与 `mm-groupthink` 的区别: 群体思维讲的是小群体为求一致而压制异议，是**凝聚力过强**的病；邓巴数讲的是群体大到无法凝聚，是**规模超限**的病。二者方向相反，对策也相反。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **确认当前规模所处的档位**
   - 完成标准: 明确写出实际人数，并标注所处档位（<15 / 15~50 / 50~150 / >150），以及是"逼近阈值"还是"已跨过"。
   - 判停条件: 若人数远低于 150 且用户抱怨的是别的问题（激励、能力、目标不清），跳到步骤 5 并说明本模型不适用。
2. **盘点哪些东西目前靠隐性共识在维系**
   - 完成标准: 列出 5-10 项"没人写下来但大家默认知道"的东西：谁对什么负责、需求怎么提、冲突找谁、什么算交付完成、跨团队怎么对接。
3. **标出最先会崩的那几项**
   - 完成标准: 按"一旦误解，代价多大 × 目前有多依赖熟人记忆"排序，取前 3 项。这三项是必须先显性化的。
4. **为前 3 项设计显性架构**
   - 完成标准: 每项给出具体机制（明确责任人/直接负责人、书面流程、跨部门接口人与固定同步节奏、决策记录），并写明迁移成本与过渡期安排（书中强调要规划调整适应期）。
   - 判停条件: 若某项显性化后反而会拖慢决策（如创新探索类事务），明确标注"此项保持隐性"，不要一刀切。
5. **给出阈值触发式预案**
   - 完成标准: 写出一套"当人数达到 X 时，启动 Y 机制"的预案表，让用户下一次逼近阈值时不需要重新诊断。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **人数远低于阈值时**: 30 人的团队引入 150 人规模的流程，只会把高效变官僚。书中明确说"人数达到邓巴数之前管用的流程"——暗示之前那套是有效的。
- **问题根源不是规模时**: 目标不清、激励错配、关键人能力不足，这些在 20 人和 200 人都会出问题，加流程不解决。
- **追求凝聚力的场景**: 若用户在抱怨团队不够团结，方向相反，应看群体动力学而非规模上限。

### 书中警告的失败模式 / 容易误用的地方

- **书中明示**: 它是「群体动力学稳定性」的一个阈值，同一概念可扩展到更小的群体（10~15 与 30~50 阈值）。也就是说 150 不是唯一刻度，把它当成唯一数字会漏掉更早的两次机制切换。
- （推导, 非书中明示）**把 150 当精确常数**: 它是一批人类学研究的量级估计，不是物理常数。跨过 140 还是 160 会失灵，取决于沟通密度与人员流动率。用途是提示"该准备换了"，不是预测具体哪天崩。
- （推导, 非书中明示）**用加流程替代加人/减范围**: 有时正确的解是把组织拆成若干个 150 以内的子单元，而不是在 300 人上堆流程。
- （推导, 非书中明示）**事后才用**: 等流程已经崩了再用，团队会把痛苦归因于"新人不行"或"文化变质"，而不是规模。本模型的价值几乎全在提前量。

### 容易混淆的邻近模型

- **超速增长稀释文化（hypergrowth-dilutes-culture）**: 讲的是一年内规模扩大过半导致文化稀释，关注的是**速度**；邓巴数关注的是**绝对规模与阈值**。快速扩张会同时触发两者，但对策不同（一个是文化传导，一个是架构替换）。
- **规模经济（economies-of-scale）**: 讲规模变大让单位成本下降，是规模的正向面；邓巴数讲的是规模的负向面。二者共同决定"该长多大"。
