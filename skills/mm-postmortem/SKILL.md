# 事后分析（postmortem）

## R — 原文 (Reading)

> 这个词经过引申，也指对先前出现的情况进行检查，弄清究竟发生了什么事，以及下次遇到类似情况时如何做得更好。
>
> — 《思维模型》, 第1章 少犯错 > 别相信直觉

---

## I — 方法论骨架 (Interpretation)

事后分析借自医学的"验尸"：医生要查清死亡的根本原因，而不是记录"人没了"。引申到组织里，就是一件事结束后系统性地回答两个问题——究竟发生了什么，以及下次遇到类似情况怎么做得更好。

它和一般的项目总结的区别在**目的**：总结是为了交代，事后分析是为了让组织变强。作者把它和"反脆弱"（antifragile）放在一起——每一次事故和失败都是一次免费的压力测试，前提是你真的把它转化成了结构上的改变，否则这笔学费就白交了。

正因为如此，事后分析有一个硬判据：**复盘产出的是"下次怎么做"的可执行改变，还是一份解释？** 如果产出的是后者——比如"需求变更频繁导致延期"——那它只是一份让所有人舒服的说明，下一次会原样重演。

书中提到鸭鸭搜索（DuckDuckGo）强制员工在每个项目完成后做复盘，目的就是让学习集中沉淀下来，让组织一次比一次强。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. 线上事故处理完，服务已恢复，要写事故报告。
2. 版本/项目结项，团队要开复盘会。
3. 一次活动、投放、发布会结束，需要总结得失。
4. 用户说"这个季度做得不太顺"，但说不清具体哪里出了问题。
5. 同一类问题反复出现，用户想知道"为什么我们总在同一个地方摔跤"。

### 语言信号
- "我们复盘一下这次事故"
- "项目结束了，写个总结吧"
- "下次怎么避免这种情况"
- "这次踩的坑要沉淀下来"
- "为什么我们老在同一个地方出问题"
- "postmortem / retro / lessons learned / after-action review"

### 与相邻 skill 的区分
- 与 `mm-root-cause` 的区别: 根本原因分析是复盘流程中的**一个环节**（挖穿因果链），事后分析是覆盖整场复盘的**流程框架**（时间线—原因—改进项—跟踪）。
- 与 `mm-mid-mortems` 的区别: 中期分析/事前分析发生在**项目进行中或开始前**（提前预演失败），事后分析发生在**结束之后**；判断依据是事件是否已经结束。
- 与 `mm-antifragile` 的区别: 反脆弱是事后分析要达成的**目标状态**（从冲击中变强），本 skill 是达成它的具体操作流程。

## E — 可执行步骤 (Execution)

1. **先定边界：复盘的是哪一段、范围多大**
   - 明确起止时间、涉及的系统/团队、要回答的核心问题。
   - 完成标准: 一句范围声明，参与者都能认同。
   - 判停条件: 若事件尚未结束（仍在处理中），改用中期分析，不要强行做 postmortem。
2. **重建时间线，只记事实**
   - 按时间列出发生了什么、谁做了什么、系统状态如何；暂时不写原因和评价。
   - 完成标准: 一条带时间戳的事实链，且关键节点有数据支撑。
3. **还原"当时为什么合理"**
   - 对关键决策点问：当事人当时掌握什么信息，为什么那个选择看起来是对的？
   - 完成标准: 至少 2 个关键决策点被还原；若全是"他应该想到"，说明复盘在追责，需纠偏。
4. **从时间线里挑出可改的杠杆点**
   - 每个问："改掉它，下次结果会不同吗？成本多大？"
   - 完成标准: 得到 3-5 个杠杆点，按"影响 × 可行性"排序，只取前 2-3 个。
5. **把杠杆点写成带 owner 和日期的改进项**
   - 每条写清：改什么、谁负责、什么时候完成、怎么验证完成。
   - 完成标准: 每条都有 owner + 日期 + 验证方式；出现"加强意识""下次注意"即为不合格，退回重写。
6. **约定跟踪机制**
   - 完成标准: 明确改进项在哪里被跟踪、下次何时回顾。

## B — 边界 (Boundary) ★

### 不要在以下情况使用
- 事件仍在进行中：此时应做中期分析/事前分析，而不是事后复盘。
- 只需要一份对外汇报材料：汇报与复盘的目标冲突，混做会让复盘变成免责说明。
- 影响极小、一次性、不会再发生的琐事：复盘的固定成本高于收益（推导，非书中明示）。

### 容易误用的地方
- 最常见的失败是产出"一份解释"而不是"下次怎么做的改变"：作者给出的判据正是区分这两者（书中明示）。"需求变更频繁"是解释，"需求冻结窗口 + 变更需重估排期"才是改进项。
- 复盘退化成追责大会：一旦指向个人，后续的信息会上报失真，学习就停了（推导，非书中明示）。
- 改进项列十几条等于没有改进项：组织消化能力有限，应只留前 2-3 个杠杆点（推导，非书中明示）。
- 只复盘失败不复盘成功：成功案例里同样有可复制的结构（推导，非书中明示）。
