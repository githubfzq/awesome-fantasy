# 技术负债（technical debt）

## R — 原文 (Reading)

> 软件业中著名的"技术负债"（technical debt）正是短视主义的后果。这个概念来自编写代码：如果你将短期代码修复（也称为"打补丁"）放在第一位，而不是精心设计能够长期使用的代码和流程，就会积累债务，最终只能通过未来重写代码来偿还。
>
> — 《思维模型》, 第2章 > 越来越热

---

## I — 方法论骨架 (Interpretation)

技术负债是一个借债模型：每次选择"打补丁"而不是"好好设计"，都是在向未来的自己借时间。本金是眼前省下的时间（快速交付），利息是未来每一个相关改动都要多付的成本，而到期必须**重写**才能结清。

它为什么会被不断欠下？因为本金和利息的支付时间分离——收益立刻可见（今天上线了），成本未来才到账（半年后改不动了）。这个时间错配使它成为短视主义的典型后果，结构上与温水煮青蛙、路径依赖同源。

一个常被忽略的要点是：作者强调它**不一定有害**。适度的技术负债有助于项目短期内迅速推进，在有时间窗口压力（验证需求、抢占市场）时甚至是正确的选择。关键区别在于程序员是有责任心的**观察者**——知道自己在欠债、记着这笔账、有计划偿还——还是无意识的"温水青蛙"，欠了也不知道，直到压垮为止。

判据：这次妥协是否降低了未来改动的灵活性？如果是，就记一笔债，并同时写下偿还条件与预计偿还时间。

---

## A1 — 书中的应用 (Past Application)

### 案例: 用胶带粘住坏掉的物件

- **问题**: 作者用生活中的例子类比：家里的物件坏了，用胶带粘上是最快、最便宜的处理方式，但它并不符合建筑标准与长期使用的要求。
- **方法论的使用**: 胶带方案的价值在于"当下立刻可用"，代价是"不符合标准"。问题不在用了胶带，而在于当房子要出售时，你反而要以更高的价格重新修理——当初省下的钱，加上额外的返工成本，一起在最后结算。
- **结论**: 作者提醒要"及时偿还"，否则债务会让你不堪重负，并从长远上削弱你的灵活性。同时强调技术负债本身不一定有害，关键在于使用者是有责任心的观察者，而不是无意识的温水青蛙。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 面临"赶工期 vs 做扎实"的取舍，需要判断这次妥协是否值得，以及如何留下记录。
2. 团队改动速度明显下降、故障率上升，怀疑是历史欠账累积。
3. 决定要不要重构：这笔债的利息有多高、什么时候还最划算。
4. 评审一个临时方案（硬编码、跳过测试、手工流程），需要给出放行条件。
5. 向非技术方解释"为什么不能只加功能"：把技术债翻译成时间与灵活性的成本。

### 语言信号 (用户的话里出现这些就应激活)

- "先这样吧，以后再优化"
- "这次赶时间，测试先跳过"
- "为什么加个小功能要这么久"
- "这块代码谁都不敢碰"
- "要不要重构？现在业务压力太大了"
- "technical debt / quick fix / patch / refactor / we'll fix it later"

### 与相邻 skill 的区分

- 与 `mm-boiling-frog` 的区别: 温水煮青蛙是通用的"渐变难察觉"机制，技术负债是它在软件与流程中的具体实例。技术负债带有明确的**解法语言**（记帐、利息、偿还、重写），如果只是察觉不到恶化而没有债务结构，用温水煮青蛙。
- 与 `mm-management-debt` 的区别: 管理债务/设计债务/多样化债务是同一借债结构在组织与设计领域的延伸（如该开的会没开、该做的决定拖着）；技术负债专指代码与工程流程层面的妥协。
- 与 `mm-path-dependence` 的区别: 路径依赖讲"越用越难换"的锁定（切换成本高），技术负债讲"欠得越多越不灵活"的累积（利息成本高）。技术负债会**导致**路径依赖，但两者切入点不同：一个看债务账，一个看可选路径。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **把妥协识别成一笔债，而不是"完成"**
   - 明确写出：这次省下了什么（本金：时间/人力），未来会多付什么（利息：每次改动多花的时间、故障风险、上手难度）。
   - 完成标准: 一句"我们欠了 X，代价是 Y"。
   - 判停条件: 若该取舍不影响未来灵活性（一次性脚本、可丢弃原型），记为"非债务"，停止本 skill。
2. **判断这笔债该不该欠**
   - 问：现在的时间窗口值多少钱？如果这个方向本身还没验证，欠债是合理的。
   - 完成标准: 明确给出"该欠/不该欠"的结论与理由。
3. **如果欠，就登记入账**
   - 记录位置、原因、预计影响面、偿还条件（什么信号出现时必须还）、预计偿还时间。
   - 完成标准: 有一条目化的债务记录，且偿还条件是**可观测的信号**而非"以后有空"。
4. **估算利息，排出偿还优先级**
   - 按"被改动频率 × 每次额外成本"排序，高频高痛的先还；对几乎不再触碰的部分可长期挂账。
   - 完成标准: 得到一个按利息高低排序的偿还清单。
5. **把偿还嵌入常规节奏，设不可逆预警**
   - 固定比例（如每迭代 15-20%）用于还债，而不是等一次大重构。
   - 完成标准: 有具体的比例/节奏安排，以及一条"越过就必须停下重写"的阈值线。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 一次性的、用完即弃的代码或流程（原型、验证脚本、临时数据处理）：不存在未来利息，按"非债务"处理。
- 该取舍根本不影响未来改动灵活性时：那是正常的工程权衡，不是借债。
- 把任何"我不喜欢这段写法"都记为债务：必须能指出它具体增加了哪一类未来成本（推导，非书中明示）。

### 书中警告的失败模式 / 容易误用的地方

- 作者提醒："及时偿还，否则债务让你不堪重负，并从长远上削弱你的灵活性"——这是书中明示的核心警告。
- 作者强调技术负债**不一定有害**，有助于项目短期内迅速推进；把"零债务"当目标反而是误用，会拖死需要速度的项目（书中明示）。
- 关键分野是"有责任心的观察者 vs 无意识的温水青蛙"：欠了却不记账、不设偿还条件，等于把主动选择退化成被动累积（书中明示）。

### 容易混淆的邻近模型

- 与管理债务：管理债务是同一结构在管理决策上的表现（该做的决定拖着、该给的反馈没给），判断方法是看欠债的是代码还是组织决策。
- 与路径依赖：技术负债是"欠账"，路径依赖是"锁定"；长期不还的技术负债会转化为路径依赖，此时需要同时考虑切换成本。
