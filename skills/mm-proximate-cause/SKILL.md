# 直接原因（proximate cause）

## R — 原文 (Reading)

> 直接原因（proximate cause）是直接导致某事发生的原因。《罗杰斯委员会报告》指出，挑战者号爆炸的直接原因是外部氢气罐着火。
>
> — 《思维模型》, 第1章 少犯错 > 别相信直觉

---

## I — 方法论骨架 (Interpretation)

直接原因是因果链上离结果最近的那一步——"是什么直接把这件事捅出来的"。它可见、好归因、也最容易让人产生"问题解决了"的错觉。挑战者号爆炸的直接原因是外部氢气罐着火，这句话完全正确，但毫无用处：修好氢气罐不会阻止下一次爆炸。

它之所以反复复发，是因为直接原因往往是更深层问题的**症状**。深层的东西（组织流程、激励结构、决策机制）不显眼、不好改、也没有一个明确的责任人，所以人的注意力会自然停在看得见的那一层。

关键判据是一句话：**治好这个原因，同样的事还会不会再发生？** 如果答案是"会"或"不知道"，那你手上拿的只是直接原因，得继续往下挖。罗杰斯委员会的最终结论是把根因定为"组织失效"，正是这个判据推出来的。

注意：直接原因不是"错误答案"，它是必要的中间层——先止血、再挖根。真正的问题是在止血之后就宣布结案。

---

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. 故障复盘里得出"是某某配置改错了/某某没检查"，准备写结论。
2. "同一个问题这已经是第三次了"——复发说明上次的归因停在直接原因。
3. 事故报告里责任人已经认了，但措施只有"下次注意"。
4. 用户在讲一个事故经过，描述停在"然后就炸了"的上一层。
5. 用户问"这个锅该谁背"，而归因会决定改进方向。

### 语言信号
- "原因就是他把配置改错了"
- "找到了，是那天没做检查"
- "已经修好了，应该不会再出问题"
- "怎么又出这种事"
- "这个责任在谁"
- "root cause / what caused the outage / it was a one-off mistake"

### 与相邻 skill 的区分
- 与 `mm-root-cause` 的区别: 直接原因是因果链的**最近一层**（可见、易归因），根本原因是**最底层**（改掉它同类问题不再发生）；本 skill 负责识别"你还停在哪一层"，root-cause 负责挖穿。
- 与 `mm-5-whys` 的区别: 五问法是往下挖的操作手法（连问五次为什么），本 skill 是判定"要不要继续挖"的判据；两者通常连着用。
- 与 `mm-postmortem` 的区别: 事后分析是事件结束后的整套复盘流程，直接原因是复盘过程中的一个检查点——用来防止复盘中途收工。

## E — 可执行步骤 (Execution)

1. **把用户当前的归因原样记下来**
   - 完成标准: 一句"直接原因是 X"的陈述，且 X 是具体事件而非类别（不要是"人的问题"）。
2. **做复发测试**
   - 问："如果 X 被彻底消除，同类事件还会不会再发生？"
   - 完成标准: 给出"不会 / 会 / 不确定"三选一。
   - 判停条件: 若明确"不会"，判定到此为止，说明为什么这层已经足够。
3. **沿因果链往上一层追问**
   - 至少连问两层：为什么 X 会发生？为什么没人拦住 X？
   - 完成标准: 得到一条 ≥3 层的因果链，每层都是具体事实。
4. **把措施分成止血与根治两栏**
   - 止血栏对应直接原因（恢复、回滚、加检查），根治栏对应链条上层（流程、机制、激励）。
   - 完成标准: 两栏各有至少 1 条，且根治栏的措施不是"加强意识""下次注意"。
5. **给根治措施定责任人与验证时间**
   - 完成标准: 每条根治措施有 owner 和一个可检查的时间点。

## B — 边界 (Boundary) ★

### 不要在以下情况使用
- 事故正在发生、需要立刻止血时：此时就该处理直接原因，挖根因是之后的事。
- 用户已经在做根本原因分析：不要重复提醒，直接配合深挖。
- 纯随机、无结构的一次性意外：不存在更深层原因可挖，继续追问会制造虚假因果（推导，非书中明示）。

### 容易误用的地方
- 书中通过把"直接原因"与"根本原因"对照来凸显其局限（书中明示）：找到直接原因不等于找到答案。
- 容易把直接原因写成类别词（"沟通不畅""意识不足"）：这类归因无法验证也无法消除，等于没归因（推导，非书中明示）。
- 容易让挖根因变成追责：罗杰斯委员会最终定的是"组织失效"这一结构性根因，而不是某个操作者；把根因落到个人身上会让后续上报失真（推导，非书中明示）。
