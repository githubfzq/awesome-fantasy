# 根本原因（root cause）

## R — 原文 (Reading)

> 相比之下，根本原因（root cause）是某事发生的真正原因。人们对自己做法的解释大同小异，任何人都可以为自身行为提供理由，但那可能并不是他们做事的真正原因。
>
> — 《思维模型》, 第1章 少犯错 > 别相信直觉

---

## I — 方法论骨架 (Interpretation)

治疗的比喻是最精确的：症状是发烧，疾病是感染。**治疗症状**是退烧——人舒服了问题看起来解决了；**治疗疾病**是消除感染——烧自然退且不复发。根本原因指的是后者。

为什么找到它这么难？因为**人给出的解释不等于真正的原因**。这不是说人在撒谎，而是：任何人都能为自己的行为提供一个说得通的理由，而这个理由是事后建构的、社会可接受的、且常常是自我保护性的。一个表现不佳的员工每次都能给出合理借口（需求变更、资源不够、别人没配合），这些可能都是真的，但真正的原因也许是缺乏技能、缺乏动力、或缺乏努力——那些才是消除后会改变结果的东西。

因此本模型有一个明确的**不信任默认**：不接受当事人（包括自己）给出的第一层解释，也不接受"执行没到位"这类万能归因。

关键判据（一问定真假）：**把这个原因消除了，同类事故还会不会发生？** 会 → 这不是根本原因，继续挖。不会 → 可能找到了。

与之相对的是**直接原因（proximate cause）**——时序上最接近事件的那个动作（"他点错了按钮""密封接缝破裂了"）。直接原因好找、好归因、也好甩锅，但它消除之后同类问题必然再发生，因为产生它的结构还在。

## A1 — 书中的应用 (Past Application)

### 案例: "挑战者"号的真正原因与员工的合理借口
- **问题**: 作者要说明直接原因与根本原因的差距有多大，以及为什么表层解释总是看起来很合理。
- **方法论的使用**: 两个对照。其一，"挑战者"号失事的直接原因链是 O 形垫圈在低温下失效；但作者指出，**根本原因是 NASA 的组织失效与缺乏内部制衡**——正是这个结构性问题让发射当天低于华氏 29 度的安全警告在会议上被忽略。其二，在组织里，表现不佳的员工每次都能给出合理的借口，而真正的原因却可能是缺乏技能、动力或努力——借口解释了这一次，真正原因解释了每一次。
- **结论**: 只处理直接原因，等于只换掉那个 O 形垫圈；只要"组织缺乏制衡"还在，下一个被忽略的警告迟早出现。判断是不是根本原因，看的不是解释有多合理，而是"消除了它，同类问题还会不会再来"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **问题反复发生，修了又来**: 同类故障第三次出现、同样的交付延期循环上演、同一个客户投诉重复出现。
2. **当事人给出的解释太顺、太完整**: 每个环节都有人给出了合理说明，但事情还是出了问题——这恰恰是危险信号。
3. **复盘时大家只想快点结束**: 找到"某人的失误"作为结论，然后散会。
4. **表现问题被归因于态度**: 员工/团队表现不佳，用户准备归因于"不上进"，需要看清是能力、动力、还是结构问题。
5. **需要设计长期有效的修复**: 不只想让这次过去，而是想让它不再发生。

### 语言信号 (用户的话里出现这些就应激活)

- "这已经是第三次了"
- "修完过一阵又出问题"
- "每次都有合理的解释，但事情就是没做好"
- "到底根本原因是什么"
- "我们是不是一直在治标"
- "换个人是不是就好了"
- "What's the root cause?" / "Treat the disease, not the symptom." / "This keeps happening."

### 与相邻 skill 的区分

- 与 `mm-5-whys` 的区别: 五问法是**挖掘工具**（通过反复追问抵达根本原因）；根本原因是**目标**（你要找到的那个东西）。书中用五问法来示范如何找到根本原因，二者是方法与目的的关系。
- 与 `mm-proximate-cause` 的区别: 直接原因是时序上最接近的表层动作；根本原因是消除后问题不复发的结构性原因。本 skill 的核心判据就是用来把这两者分开的。
- 与 `mm-unforced-error` 的区别: 主动失误判定的是"这一分是不是自己送的"（单次归因）；根本原因找的是"为什么会一直送分"（结构归因）。前者针对事件，后者针对系统。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **区分：这是反复发生的问题，还是一次性事件**
   - 完成标准: 确认该问题此前是否发生过、发生过几次、上次是怎么修的。
   - 判停条件: 若是明确的一次性偶发事件（外部突变、不可重复的条件），直接修复即可，不必做根本原因分析——本 skill 的收益来自防止复发。
2. **收集表层解释，并标记为"待验证"而非"结论"**
   - 完成标准: 完整记录当事人给出的所有解释（包括自己的第一直觉），明确标注它们都只是**候选**，因为"任何人都可以为自身行为提供理由"。
3. **区分直接原因与候选根因**
   - 完成标准: 写出时序链上最接近事件的直接原因（谁做了什么），再列出 2-4 个更深的候选原因（流程缺失、激励错位、能力缺口、信息不通、缺乏制衡）。
4. **对每个候选根因施加关键判据**
   - 完成标准: 对每个候选问"把这个原因消除了，同类事故还会不会发生？"——给出是/否及理由。答"会"的直接淘汰。
   - 判停条件: 若所有候选都过不了判据，说明挖得不够深，回到第 3 步继续下探（此时应配合 5-whys 逐层追问）。
5. **寻找佐证：这个根因还能解释别的现象吗**
   - 完成标准: 给出至少 2 个"同一个根因导致的其他症状"。能解释多个现象的根因才更可能是真的；只能解释这一次的，多半还是表层。
6. **给出修复方案并明确它是治本还是治标**
   - 完成标准: 每个修复动作标注：消除的是症状还是原因。若资源有限只能先治标，明确写出"这是临时措施，根因未除，同类问题会再发生"，并给出根治的后续计划。
   - 判停条件: 若最终结论指向"某个人的问题"，明确警告：追责到人通常意味着还没挖到根因（应检查是不是流程、培训或激励机制的问题），这与基本归因错误直接相关。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **一次性偶发事件**: 直接修复更快。为一次不会重现的问题做完整根因分析是浪费。
- **需要立即止血的事故现场**: 先止血（stop-the-bleeding）、恢复服务，事后再做根因分析。两件事混在一起会导致在压力下草率归因。
- **用来追责与惩罚**: 一旦目的变成"找到该罚的人"，人们会开始隐瞒信息，根因分析赖以工作的诚实数据就没了。

### 书中警告的失败模式 / 容易误用的地方

- **书中对本模型未给边界**（`boundary` 字段为"书中未提"），以下为基于机制推导的警告（推导, 非书中明示）：
- **把直接原因当根本原因**: 最常见也最危险的失败。换掉 O 形垫圈之后，人们以为问题解决了。识别方法是第 5 步——真正的根因通常能解释一串现象。
- **接受过于顺滑的解释**: 一个太完整、太合理的故事，往往是事后建构的。这也正是"别相信直觉"这一节的标题所警告的。
- **无限上溯**: 任何原因都还有更深层的原因（"组织失效"上面还有"行业压力"）。挖到"可被本层级改动的那一层"就该停——再往上就变成了无法行动的哲学。
- **追责到人即止步**: 结论为"某人责任心不强"通常不是根因，而是根因的症状。应继续问：什么样的流程会让一个责任心不强的人处在这个位置而不被发现？

### 容易混淆的邻近模型

- **五问法（5-whys）**: 是找到根本最常用的挖掘工具，与本模型配套使用。
- **基本归因错误（fundamental-attribution-error）**: 是把问题归因于人的品性而非处境的偏差，是根因分析中最容易掉进去的坑（结论停在"某人不行"）。
