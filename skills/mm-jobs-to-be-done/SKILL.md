# 待办任务（jobs to be done）

## R — 原文 (Reading)

> “人们不是想买1/4英寸口径的电钻，而是想要一个直径为1/4英寸的洞”
>
> — 《思维模型》, 第9章 > 缺少执行的愿景不过是幻想

---

## I — 方法论骨架 (Interpretation)

客户买的从来不是你的产品，他买的是**他想办成的事**。这句被引滥的话有一个很锋利的推论：如果你盯着产品在优化，你可能正在优化一件客户根本不在乎的事。

电钻只是手段，墙上那个洞才是他想要的。而顺着再追问一层往往更值钱——他要那个洞通常是为了挂上照片，他挂照片是为了让家里显得像自己的家。同一个物理产品，可以处在完全不同的任务链条上。

这个模型的有用之处在于**识别错位**。书里强调：一旦弄清真实用途，你就可以围绕它重设产品和营销。很多时候这也解释了为什么一个"功能很差"的产品能在市场上赢——它在真正的任务上做得足够好。

书里还点了一条很实用的约束：**如果一个产品要同时完成两项任务，它通常至少有一项做不好**。这不是执行力问题，而是因为两项任务的优化方向常常相互冲突（例如"快速提神"和"好喝有饱腹感"对一杯饮品来说就是互斥的）。所以发现产品身上挂着两个不同的任务时，正确做法往往是**拆成两款**，而不是做一款更强的。

同时也求了这个模型在自己身上的用法：**问自己"他们实际上是雇我来做什么的"**，据此判断当前策略是否有效、甚至是否需要转型。

判据一句话：**客户在什么情境下、动了什么念头、才决定"雇"这个东西？**

一个必要的防波堤（见边界）：这个模型实施时最隐蔽的失败，是**客户指定错误的解决方案**。一本书里给的对应做法是——请客户先用通俗语言解释他想达到的目标，而不是让他描述他想要的功能。

## A1 — 书中的应用 (Past Application)

### 案例: 快餐店奶昔的双任务
- **问题**: 一家快餐店的奶昔销量停滞，团队按常规方式改进产品（更稠/更甜/更便宜/加果粒），试了各种配方都没有效果。
- **方法论的使用**: 研究者不再问"你想要什么样的奶昔"，而是去问"你是在什么情境下、为了做什么才买这杯奶昔的"。结果发现顾客实际上在做两件完全不同的事：约有一半的顾客是在早高峰买它，目的是**让漫长无聊的上班路程变得有趣一点**——一杯能喝很久、稠到喝到最后一口还有东西吸的东西；而另一些顾客（典型的是父母给孩子买）要的是完全不同的东西，来自另外的时间段的另一套期待。
- **结论**: 因为这两份工作所需的属性几乎相互冲突，同一个产品不可能同时做好。真正的解法不是把奶昔做得"更好"，而是**按任务把它拆开**——围绕任务重设产品与营销，而不是在产品属性上继续堆料。作者用它说明：看不见客户的真实任务时，所有的产品优化都可能是白做的。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **同一款产品被完全不同的人用、呈现随机感**: 用户抱怨"我们也不知道用户都是些什么人"，需要识别不同的任务簇。
2. **产品改了又改进就是不见效**: 需要在改进产品之前先确认是不是没有击中真正的任务。
3. **用户的买法和用法与设计的意图完全不同**: 这是一个信号而不是用户的失误，需要欣喜地去追。
4. **判断当前策略是否有效、甚至要不要转型**: 用户自问"他们实际上是雇我来做什么的"，据此调整。

### 语言信号 (用户的话里出现这些就应激活)

- "他们到底买我们的东西干嘛？"
- "用户的使用方式跟我们设计的完全不一样"
- "明明功能比对手强却卖不过"
- "我们的用户画像太杂了，什么人都有"
- "客户一直要我们加某个奇怪的功能"
- "我真的不知道他们看中我们哪一点"
- "What job does the customer hire us for?" / "We don't know why people buy this." / "Users use it in unexpected ways."

### 与相邻 skill 的区分

- 与 `mm-customer-development` 的区别: 客户开发是**整套快速反馈循环的流程**（怎么安排访谈、多快一轮），待办任务是这循环里**最关键的那个提问内容**（客户雇你干什么）。前者管方法，后者管问什么。
- 与 `mm-personas`（用户角色模型） 的区别: 用户角色按人口属性/行为特征给人贴标签（年龄、职业、使用频次），待办任务按**情境与动机**归类（在什么时刻、想做成什么事）。同一个 persona 内部可能藏着两个互斥的任务，这是persona 模型看不出来的。
- 与 `mm-maslow-s-hammer` 的区别: 马斯洛之锤描述的是我们自己只会用熟悉方案敲所有钉子的偏误，待办任务是纠正它的具体工具——把注意力从"给他什么方案"拉回到"他要办什么事"。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **按情境而不是按人群把客户切开**
   - 完成标准: 得到若干"XX 时刻 / 想做成 YY"的表述。若切出来的东西是"25-35 岁白领"这类人口标签，不合格，需重做。
   - 判停条件: 若切不出至少两个有差异的情境，说明信息不足，先回到客户开发补充访谈。
2. **追问任务链的三层**
   - 完成标准: 对每个情境写出三行：表层要完成的动作（打一个洞）→ 真正想要的结果（把照片挂上墙）→ 情感和动机层面（让这个家看起来像自己的家）。至少追到第二层才有效。
3. **请客户用通俗语言描述目标，而不是听他给方案**
   - 完成标准: 访谈提纲的问题全部以"上次你遇到这事是什么时候""当时你最后怎么解决的"开头，禁止出现"你觉得我们的 XX 功能好不好"。这是书里给出的具体做法：客户容易把关注点放在特定解决方案上，请他先用通俗语言解释想达到的目标。
4. **检查是否挂了两个互斥的任务**
   - 完成标准: 对每个任务列出它要求的属性清单，检查两个任务的属性是否有冲突项（如"耐喝" vs "好喝快速"）。若有冲突，给出明确的建议：**拆成两款产品/两条业务线**，而不是继续做一款"更好的"。
5. **围绕任务重设产品与营销**
   - 完成标准: 对每个主任务给出具体的改动清单，覆盖三个地方：产品/服务的形态（哪些该做、哪些该砍）、用户获取时的措辞（要对着那个任务说话）、竞争中真正要比的是谁（往往是另一品类，不是同行）。
6. **反向自查：他们实际上雇我来做什么**
   - 完成标准: 明确回答这个问题，并据此给出结论——当前策略是在服务那个真实任务，还是在服务一个我们自己想象的任务。若错位严重，转介 `mm-pivot` 讨论转型。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **客户已经能清楚陈述目标且产品明显对准**: 继续深挖没有增量，直接改进执行即可。
- **问题纯粹是价格、性能、可用性这些已知变量**: 这时该做的是取舍与排期，而不是重新找任务。
- **客户要求提供高度定制化的工程实现时**: 需求非常具体且双方没有误解空间，追问"真实任务"会显得拒绝配合。

### 书中警告的失败模式 / 容易误用的地方

- **书中明示**: 要警惕**客户指定错误的解决方案**。这是最隐蔽的陷阱——客户非常真诚地告诉你他要什么功能，但那只是他脑子里第一个蹦出来的方案。一旦照做，你会精确地做出一个错的东西。
- **书中明示**: 劳伦的经验是**请客户先用通俗语言解释想达到的目标**。这是绕开上述陷阱的具体手法，务必照做（见 E 段第 3 步）。
- （推导, 非书中明示）**把同一批人当成同一件事**: 同一个人在不同情境下会雇用同一个产品去完成完全不同的任务，按 persona 而不是按情境分析会漏掉这一点，得出不可用的平均结论。
- （推导, 非书中明示）**追到一半就停**: 只停在动作层（要一个洞）会给出自明而无差异的结论，价值在第二层第三层。第 2 步要求至少追到第二层。
- （推导, 非书中明示）**发现两个任务却硬要做成一款**: 这正是奶昔案例的反面，书中的结论很明确——同时完成两项任务通常至少有一项做不好。

### 容易混淆的邻近模型

- **用户角色模型（personas）**: 按人群属性划分，容易掩盖同一 persona 内部的任务差异；待办任务按情境与动机划分，两者互补但不能互相替代。
- **待办任务与产品/市场匹配（product）**: 找到并利用真实任务是达成匹配的主要手段之一；反过来，迟迟找不到任务通常意味着还没达成匹配。
