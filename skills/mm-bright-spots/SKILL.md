# 亮点（bright spots）

## R — 原文 (Reading)

> 如果答案还是不明确，不妨看一看你有没有亮点（bright spots）。所谓的“亮点”，就是众多消极迹象中的积极迹象。
>
> — 《思维模型》, 第9章 > 缺少执行的愿景不过是幻想

---

## I — 方法论骨架 (Interpretation)

当整体判断"要不要继续"迟迟给不出答案时，不要只在总量上权衡好坏，而要去找**众多消极迹象中的积极迹象**——这就是**亮点（bright spots）**。

**它描述什么**：在商业上，亮点表现为一小群特别喜欢、并且积极使用你产品的客户；在职业上，表现为当前工作中你真心喜欢的部分。它们的共同特征是：数量不大，但强度异常高，与周围的消极形成反差。

**为什么成立**：总体平均值会把信号抹平。一个"整体不行"的项目里，往往藏着一个"对某些人极其行"的角落——这个角落才是真正的信息，因为它说明价值在某处确实被创造了。平均值只告诉你现状不好，亮点告诉你**好在哪里、为什么好**，而"为什么好"是可复制的。

**关键判据有两个**：

1. **有没有亮点**。长期找不到亮点，就该考虑转型。
2. **亮点够不够多**。找到亮点之后要问：这些部分"多到足以让你留下吗"。有亮点不等于该留下，亮点太少只能证明还没死，不能证明值得继续。

**找到之后怎么用**：弄清这个亮点为什么顺利，以此为立足点集中推进——也就是把它变成滩头堡。

书中给了一句极重要的边界："你用不着退回原点，但也不能待在原地。" 找不到亮点不是立即归零的理由，但也不是继续停滞的借口。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 想转行/离职，但说不清是"真的该走"还是"只是一时不顺"，反复权衡没有答案。
2. 产品数据全面难看（增长停滞、留存低），但隐约有一小撮用户用得特别狠。
3. 一个项目/一段关系整体失败，要决定是砍掉重来还是找个口子继续。
4. 团队士气低迷，人人都在抱怨，需要找到还能撬动的地方。
5. 已经盘点了很久"哪里不好"，越盘越丧，需要换一个看问题的方向。

### 语言信号

- "整体都不行，但好像还有一点点好的地方"
- "这份工作还有什么值得留恋的吗"
- "我要不要转行 / 要不要辞职"
- "我们的用户里有没有特别喜欢我们的"
- "这个项目还有救吗"
- "已经盘了一堆问题，越盘越没信心"
- "bright spots / what's working / any positive sign / should I keep going / is there anything worth staying for"

### 与相邻 skill 的区分

- 与 `mm-beachhead` 的区别: 亮点是**诊断工具**——用来在消极中定位积极迹象、判断该不该继续；滩头堡是**行动方案**——确定要继续之后，选一个窄口子站稳再扩张。先找亮点，再把亮点变成滩头堡。
- 与 `mm-pivot` 的区别: 转型处理的是**整体方向要不要换**以及换到哪里；本 skill 处理的是**在换与不换之间的诊断**。本 skill 的输出（有没有亮点、亮点够不够）恰恰是转型决策的输入。
- 与 `mm-exit-strategy` 的区别: 退出策略讲**怎么体面地退**、退路怎么设计；本 skill 判断**该不该退**。长期找不到亮点时才转向退出。
- 与 `mm-jobs-to-be-done` 的区别: 待办任务追问"用户雇你的产品去完成什么工作"，是需求的归因分析；本 skill 只要求先定位**哪里出现了反常的积极反应**，不预设归因框架。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先让用户把"整体不行"拆成清单**
   - 完成标准: 得到一份具体的消极项列表（不是笼统的"都不行"），每项可指认到具体对象/环节/时间段。
2. **在清单里强制找亮点**
   - 完成标准: 至少找出 1-3 个"反常的积极迹象"，每个都要写明：是谁（哪个用户/哪项工作/哪段时间）、强度如何、与周围的反差有多大。
   - 判停条件: 若穷尽后确实一个都没有——明确告知"无亮点"，跳到步骤 5，不要硬凑。
3. **问"为什么这里偏偏顺利"**
   - 完成标准: 对每个亮点给出一条可验证的成因假设（不是"运气好"），并指出验证这条假设最少需要看什么数据/问什么人。
4. **做留存判断：亮点够不够多**
   - 完成标准: 直接回答书中那个问题——"这些部分多到足以让你留下吗"。给出明确的二分结论 + 支撑理由。若答案是"不够"，转向转型/退出讨论。
5. **给出去向，不留悬空**
   - 完成标准: 有亮点且够多 → 指出应以此为立足点集中推进（可转 `mm-beachhead`）；有亮点但不够 → 指出可放大的具体动作与观察期；无亮点 → 指出已到考虑转型的时点，并引用书中边界："你用不着退回原点，但也不能待在原地"。
   - 完成标准补充: 必须给出一个明确的复查期限，避免盘点变成无限期拖延。

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 局面本来就顺利，只是在做优化——没有"消极中的积极"可找，直接做常规分析。
- 纯事实或技术排查问题（如"这个 bug 为什么出现"）——亮点模型不提供因果诊断能力。
- 已经明确要转型、正在挑新方向——那是转型/滩头堡的任务，本 skill 已无诊断价值。
- 用户要的是情绪安抚——本 skill 会持续追问"够不够多"，可能加重不适，应先处理情绪。

### 容易误用的地方

- 书中明示: **"你用不着退回原点，但也不能待在原地。"** 找不到亮点不等于立刻归零，但也不能停滞——两个方向都不能走极端。
- （推导, 非书中明示）把个别亮点当成整体可行的证据。亮点是线索不是结论，需要回到步骤 4 的"够不够多"再判断一次，否则就是幸存者式自我说服。
- （推导, 非书中明示）只盘点不决策。亮点盘点的价值全在"够不够留下"这个二分判断上，盘完不下结论等于用分析缓解焦虑。
- （推导, 非书中明示）把亮点当成不做功课的借口。找到亮点之后必须回答"它为什么顺利"，否则无法复制、也无法放大。
