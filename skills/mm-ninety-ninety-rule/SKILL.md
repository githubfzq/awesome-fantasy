# 九九定律（ninety-ninety rule）

## R — 原文 (Reading)

> 开发软件时，前90%的代码要花90%的开发时间，剩余10%的代码要再花90%的开发时间。

> — 《思维模型》, 第3章 > 摆脱坏习惯

---

## I — 方法论骨架 (Interpretation)

九九定律是一条关于**收尾被系统性低估**的经验规律：前 90% 的工作花掉 90% 的时间，剩下的 10% 还要再花 90%。它得名于 1985 年汤姆·卡吉尔在贝尔实验室编程时的观察。

注意它的数字是刻意"加起来超过 100%"的——这是修辞，也是重点：**最后那 10% 的昂贵程度与前面 90% 相当，而不是它的九分之一。** 收尾之所以贵，是因为它包含了所有在乐观规划时看不到的东西：联调、边界情况、环境差异、文档、评审返工、以及"这个也要改一下"的连锁反应。

它与侯世达定律同构：两者都在说"低估工期是普遍现象"，只是九九定律把镜头对准了**收尾这一段**。侯世达说整体都会超，九九定律说超得最狠的是最后那一段。

关键判据是：**"进度 90%"是一个几乎无意义的数字**。因为剩下的 10% 可能还要再花掉与前 90% 相当的时间，所以"90% 完成"既不意味着快到了，也不能用来推算剩余时间。

作者给出的对策很直接：**定期询问"哪些部分算完成了"**，避免把精力浪费在无尽收尾上。这是一个通过重新定义完成标准来主动结束项目的动作，而不是靠加班把尾巴磨完。

---

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 项目长期停在"90% 完成"，报表上一直显示快好了但就是交付不了。
2. 主体工作早已做完，剩下联调、测试、文档、上线流程拖了几周。
3. 团队或个人在收尾阶段陷入无止境的打磨，看不到终点。
4. 管理者看到"进度 90%"的汇报，需要判断真实剩余工作量。
5. 制定排期时需要为收尾单独留出与主体相当的时间块。

### 语言信号

- "功能都写完了，就剩联调"
- "报告内容都有了，还在润色"
- "90% 都做好了，就是上不了线"
- "最后这点收尾怎么这么久"
- "快好了，可能还要一两周吧"
- "ninety-ninety rule / last 10 percent / almost done but not shipping"

### 与相邻 skill 的区分

- 与 `mm-hofstadter-s-law` 的区别: 侯世达定律说**整体估算普遍偏低**，九九定律特指**收尾那一段被系统性低估**。给整份排期定系数用前者，已经陷在"就差最后一点"的泥潭里用本 skill。
- 与 `mm-perfect-is-the-enemy-of-good` 的区别: 完美乃优秀之敌处理的是**质量标准过高**的取舍（该不该接受"够好"），九九定律处理的是**收尾工作量被低估**的估算问题。一个是心态，一个是结构。
- 与 `mm-premature-optimization` 的区别: 过早优化是**在早期做了不该做的优化**（顺序错误），九九定律的收尾成本往往是**必须做但没被算进去**的工作（遗漏）。

## E — 可执行步骤 (Execution)

1. **质疑"90% 完成"这个数字**
   - 问：这个百分比是按什么算的？按代码行数、按任务数、还是按已验证的功能数？
   - 完成标准: 明确现有进度口径，并指出它为什么不能推算剩余时间。
   - 判停条件: 若进度是按"已验证可用"计且剩余项可枚举，可直接进入步骤 3。
2. **把剩下的 10% 全部枚举出来**
   - 强制列出所有未完成的收尾事项，不许用"等等""还有一些"带过。
   - 完成标准: 得到一份具体清单，每项可指派、可验证。
3. **对收尾重新估时，量级对齐主体**
   - 按九九定律的提示，给收尾整体一个与主体工作同量级的估算，而不是按"10% 的工作量"估算。
   - 完成标准: 收尾估时达到主体估时的 50%-100%，且能逐项说明依据。
4. **定期追问：哪些部分算完成了？**
   - 用作者给的抓手，周期性重开这个问题，主动划定完成边界。
   - 完成标准: 明确写出"本次交付包含什么、明确排除什么"，并得到相关方确认。
   - 判停条件: 若某收尾项被判定为"非本次必需"，直接移出范围，不进入估算。
5. **为下一个项目回填收尾系数**
   - 记录本次主体与收尾的实际耗时比，作为下次排期的校准数据。
   - 完成标准: 产出一个可复用的收尾/主体比值。

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 整体排期与资源规划阶段：用侯世达定律做全局校准，本 skill 聚焦收尾段。（推导，非书中明示）
- 收尾拖长是因为有人在无限提高质量标准：那是完美乃优秀之敌，需要的是取舍决策而非重新估时。（推导，非书中明示）
- 高度标准化、收尾流程固定的交付（例行报表、流水线作业）：收尾成本已知且稳定，不需要这条经验法则。（推导，非书中明示）

### 容易误用的地方

- 把"90%"当成真的完成了九成。这个数字的分母往往是"写代码"而不是"交付"，因此严重高估实际进度。（书中明示）
- 用加班去磨收尾，而不是重划完成边界。作者给的对策是定期追问"哪些部分算完成了"——是减法不是加法。（书中明示）
- 把数字当精确公式。原文是经验观察，比例随项目类型变化，不应当成 1.8 倍工期这样的硬常数。（推导，非书中明示）

### 容易混淆的邻近模型

- 与侯世达定律：整体低估 vs 收尾低估，是同一现象的全景与特写。
- 与完美乃优秀之敌：一个说"收尾工作量被漏算了"，一个说"质量标准定得太高了"。收尾既长又无意义时，两个模型同时成立。
