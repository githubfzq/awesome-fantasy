# 过早优化（premature optimization）

## R — 原文 (Reading)

> 在计算机领域，这种陷阱被称为"过早优化"（premature optimization），也就是你提前太多（过早）调整或完善代码与算法（做优化）。
>
> — 《思维模型》, 第1章 少犯错 > 保持简洁，笨蛋！

---

## I — 方法论骨架 (Interpretation)

过早优化描述的是一种**顺序错误**：在支撑方案的假设还没被检验之前，就把资源投入到"让它更好"上。

优化动作本身有成本，而且往往不可逆——把代码重写成高速版本、把流程打磨精细、把方案做到 90 分，这些投入全都建立在"这个方向是对的"这个前提上。一旦假设被推翻，前提消失，前期投入全部沉没：你不但没省时间，还多花了一轮。

它反对的不是优化，而是"过早"。正确的顺序是先做一个粗糙但能验证的东西，等反馈确认方向，再打磨。书里给的行动准则是"在得到真实反馈之前，请尽量少做无用功"。

判据只有一句：**在我投入优化之前，支撑这次优化的假设是否已经过检验？**

书中案例：认定亲戚一定会来，提前订好食宿行程，结果亲戚来不了，只能回头更改所有预订——优化投入全部作废。

---

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 需求或方向还没确认，用户就要开始做性能调优、架构重构、UI 精修。
2. 用户为一个还没验证的方案写详细计划、买工具、搭框架、招人。
3. 用户纠结"用哪个框架更快""哪个方案最优"，而核心假设（有没有人要）还一次都没问过。
4. 复盘时发现做了一堆东西全废了，需要定位是不是顺序错了。
5. 用户提出"反正以后也要做，不如现在一次做到位"，需要检验这个理由。

### 语言信号

- "先把性能做上去再说"
- "这个方案我要做到 90 分再拿出去"
- "反正以后也要做，不如一次做到位"
- "我提前把食宿都订好了"
- "Let's optimize this before we ship."
- "premature optimization / don't optimize too early"

### 与相邻 skill 的区分

- 与 `mm-minimum-viable-product` 的区别: MVP 是正面动作（**先做什么**），过早优化是负面警戒（**别先做什么**）。两者共用同一个判据"假设验证了吗"，MVP 给出的是验证路径。
- 与 `mm-perfect-is-the-enemy-of-good` 的区别: 完美主义讲的是质量标准过高导致迟迟不交付（卡在"不够好不敢发"）；过早优化讲的是投入顺序错误导致返工（卡在"还没验证就打磨"）。前者的问题在出口，后者的问题在入口。
- 与 `mm-parkinson-s-law` 的区别: 帕金森定律说工作会膨胀到填满所有时间，是消耗在无关紧要处；过早优化是消耗在真实但为时过早的事情上，方向不同。

## E — 可执行步骤 (Execution)

1. **列出当前方案依赖的关键假设**
   - 完成标准: 写出 1-3 条可证伪的假设（"用户愿意为 X 付 Y 元""流量来自 Y 渠道"），每条都要有"如果错了我能看出来"的特征。
2. **逐条标注假设是否已验证**
   - 完成标准: 每条标"已验证 / 未验证"，已验证的注明证据来源与验证时间。
   - 判停条件: 若全部已验证，直接跳到步骤 4——此时再做优化已不属于过早。
3. **为未验证的假设设计最便宜的验证动作**
   - 完成标准: 给出一个成本最低、最快能拿到真实反馈的动作（问 5 个用户 / 做个假门 / 发一版粗糙的），并明确验证通过的标准。
4. **把优化动作冻结到验证之后**
   - 完成标准: 明确写出"在 X 被验证之前，不做 Y 优化"，并给出重新评估的触发条件或时间点。
5. **验证后重新评估优化项**
   - 完成标准: 用验证结果重新筛一遍当初想做的优化，列出哪些现在值得做、哪些被证伪后彻底不必做。

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 安全、合规、数据正确性、隐私这类不可回退的硬约束——这里的"优化"其实是底线要求，不能等验证完再做。
- 假设已经验证、产品进入成熟期的常规性能与成本优化——那是正常工程节奏，不是过早。
- 优化本身成本极低且完全可逆（改个变量名、调个参数）——套这个模型反而拖慢节奏。

### 容易误用的地方

- 书中未给出具体局限，只说"在得到真实反馈之前，请尽量少做无用功"。
- （推导，非书中明示）把"过早优化"当成不做任何设计的挡箭牌。模型反对的是**在错误假设上的不可逆投入**，不是反对思考。
- （推导，非书中明示）反向误用：假设早已验证却还以"避免过早优化"为由无限期推迟必要的优化，把模型变成了积累技术债的借口。
