# 用户角色模型（personas）

## R — 原文 (Reading)

> 这种思考方式有助于你创建用户角色模型（personas），也就是代表你理想客户的虚拟角色。它能帮你切实评估自己的创意，以便更好地进行推理。
>
> — 《思维模型》, 第9章 > 缺少执行的愿景不过是幻想

---

## I — 方法论骨架 (Interpretation)

用户角色模型就是**代表你理想客户的虚拟角色**。它的用途很具体：帮你切实评估创意、更好地推理。

**为什么有效**：抽象的"用户"可以被任意塑造——任何人都能说"用户会喜欢的"，因为没人能反驳一个不存在的对象。一旦把用户换成一个**具体的、有名字的、基于真人构建的角色**，争论就有了裁判："鲍勃会做这件事吗？"这个问题是可以被追问、被检验、被反驳的。

**关键的操作约束（书中最重要的一条）**：角色应当**基于真实客户开发所得的真人构建**，不是凭空想象出来的。这决定了角色模型的可靠性——它其实是真人观察的压缩包。

**用法有两种**：

1. 直接问："鲍勃或莎莉会做这件事吗？"用来检验方案。
2. 借用视角换位思考——**真实、虚构或他人的视角**都可以借用，从而更有效地运用其他客户类模型（如待办任务、客户开发等）。

**为什么成立**：人的推理能力对具体对象远强于对统计群体。给一个具名角色做判断，会激活你对真实个体的全部直觉与细节记忆；给"25-35 岁都市白领"做判断，只会激活刻板印象。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品评审会上各执一词，双方都用"用户会觉得……"来互相说服。
2. 要写营销文案或落地页，需要先确定"在对谁说话"。
3. 功能优先级排不出来，因为每个功能都有人觉得重要。
4. 团队对目标客户只有模糊描述（"中小企业""年轻人"），无法做具体决策。
5. 想检验一个创意是否靠谱，但做不起一轮真实用户测试。
6. 团队远离一线，决策时对真实用户失去感知。

### 语言信号 (用户的话里出现这些就应激活)

- "用户应该会喜欢这个功能"
- "我们的目标客户是中小企业"
- "这个文案是写给谁看的"
- "站在用户角度想想"
- "到底先做哪个功能"
- "我们的典型客户长什么样"
- "user persona / would our user actually do this / who are we building for"

### 与相邻 skill 的区分

- 与 `mm-customer-development` 的区别: 客户开发是**获取真实客户认知的方法**（走出去与人交谈）；本 skill 是**把这些认知压缩成可复用的虚拟角色**。前者是数据来源，后者是使用方式——书中明确要求角色基于客户开发所得的真人构建。
- 与 `mm-jobs-to-be-done` 的区别: 待办任务关注**用户想完成什么任务**（动机与场景）；本 skill 关注**是谁**（一个具体的、可追问的人）。角色模型常包含任务，但核心是人物的具体性。
- 与 `mm-availability-bias` 的区别: 可得性偏差是**危险信号**——书中明确警告构建角色时不要让可得性偏差限制考虑的因素，只用最容易获得的数据会做出不实用的角色。本 skill 是方法，可得性偏差是它必须防范的失效模式。
- 与 `mm-what-type-of-customer-are-you-hunting` 的区别: 那个模型做的是**客户类型的战略选择**（猎大象还是猎苍蝇）；本 skill 是在选定类型之后，把它变成一个具体的、能被团队共同追问的人。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先确认有没有真实用户素材**
   - 完成标准: 检查是否已有客户开发访谈、销售记录、客服工单、用户反馈等真人素材。
   - 判停条件: 若完全没有，明确警告——书中要求角色基于真实客户开发所得的真人构建，凭空编造的角色只是刻板印象。建议先做几轮客户访谈（转 `mm-customer-development`）。
2. **从真人中提炼 2-3 个角色，不要多**
   - 完成标准: 每个角色都要有名字、具体处境、以及**来自真实观察的行为特征**（他实际怎么做的，不是我们希望他怎么做的）。超过 3 个角色会失去"可追问"的威力。
3. **明确标注每个角色基于多少个真人**
   - 完成标准: 每个角色注明素材来源与样本数。这一步是防止可得性偏差的硬约束——若某角色只基于 1 个最容易想起的人，必须标明。
4. **用它来裁决当前争论**
   - 完成标准: 把待决方案逐一代入角色，明确回答"鲍勃或莎莉会做这件事吗"，并给出理由。若出现"要看情况"，说明角色刻画不够具体，回头补。
5. **设置过期与复检**
   - 完成标准: 给出复检周期或触发条件（如进入新客群、产品方向变化、距上次访谈超过 N 个月）。角色会随真实用户变化而失效，必须定期用新的真人素材刷新。

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 完全没有真实用户素材时——先做客户开发，不要凭空造角色。
- 需要统计意义上的市场细分与规模估计——角色是定性工具，不能用来推算市场规模。
- 用它替代真实测试——角色可以筛掉明显不靠谱的创意，但不能验证一个创意真的有效。
- 用它给用户贴标签以固化偏见——角色是理解工具，不是筛选或排斥用户的标准。

### 容易误用的地方

- 书中明示：**切勿让可得性偏差限制构建角色时考虑的因素**——只用最容易获得的数据会做出不实用的角色。这是本模型唯一被明确指出的失效模式。
- 书中明示：角色应**基于真实客户开发所得的真人构建**。凭想象构造的角色会放大团队已有偏见。
- （推导, 非书中明示）把角色写成人口统计标签（年龄、职业、城市）。这类信息无法回答"他会做这件事吗"，真正有用的是他实际的行为与处境。
- （推导, 非书中明示）角色数量过多。超过 3 个后，团队会重新退回到"挑一个支持我的角色"的状态，失去裁判功能。
- （推导, 非书中明示）建完不更新。角色是真人观察的压缩包，真人变了角色就过期。
- （推导, 非书中明示）把"理想客户"理解成"我们希望拥有的客户"。书中说的是代表理想客户的虚拟角色，但仍须以真人为基础——两者冲突时以真人为准。

### 容易混淆的邻近模型

- **客户开发（customer development）**: 真人素材的来源；本 skill 是把素材压缩成角色。
- **待办任务（jobs-to-be-done）**: 关注用户要完成什么；本 skill 关注是谁。
