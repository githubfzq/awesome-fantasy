# KISS原则（Keep It Simple, Stupid!）

## R — 原文 (Reading)

> 以上建议和本节中的所有建议都可以简称为"KISS"——保持简洁，笨蛋！（Keep It Simple, Stupid!）
>
> — 《思维模型》, 第1章 少犯错 > 保持简洁，笨蛋！

---

## I — 方法论骨架 (Interpretation)

KISS 是工程界的一句老话，在书里被用作第 1 章这一整节方法的总纲：**先用奥卡姆剃刀把假设削到最少，再用最低成本的方式去检验它**。两件事的顺序不能颠倒——先简化，再验证；跳过验证的简化是偷懒，跳过简化的验证是浪费。

它成立的理由很实际：复杂度是有成本的。每一条多余的假设、每一个多余的模块、每一个多余的会议，都要占用注意力、引入出错机会、增加维护负担，而且往往是为了"以防万一"而加的，从来没被真正用过。同时，简单的方案更快落地，也就更快拿到真实反馈——反馈本身就是信息，比在纸面上把方案推演得更完美更有价值。

需要说清的是，KISS 不是"越简单越好"的审美主张，而是**在效果相当的前提下取更简单的那个**的策略原则。判据是：**我当前的方案里，有没有可以删掉而不影响结论/效果的部分？** 有，就删掉，然后再问一遍。

---

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?
1. **方案写了好几页还讲不清**：项目计划、产品需求、活动方案堆积了大量分支与例外，需要砍到一页能说清。
2. **还没验证就在搭完整系统**：想先做权限体系、先建数据中台、先搭微服务，而核心假设一次都没验证过。
3. **解释一件事用了一长串前提**：给老板/客户解释结论时讲了十分钟背景，需要找到那个一句话版本。
4. **流程/会议/文档没人用**：存在只为"以防万一"，实际从未触发过。
5. **在多个方案间纠结，其中一个明显更轻但看起来"不够专业"**（推导, 非书中明示）。

### 语言信号
- "我是不是把这个想复杂了"
- "有没有更简单/更省事的做法"
- "这个方案能不能先做一版小的"
- "流程越搞越绕了"
- "说实话这一块好像从来没用过"
- "Can we keep it simple?" / "What's the simplest version of this?"

### 与相邻 skill 的区分
- 与 `mm-ockham-s-razor` 的区别: 剃刀是关于**解释与假设选择**的认识论原则（哪个解释更可能为真）；KISS 是关于**做事与设计**的实践偏好（怎么实现更省事）。可以说 KISS 把剃刀用到了工程上。
- 与 `mm-minimum-viable-product` 的区别: MVP 是"做出能验证核心假设的最小产品"这一具体产物；KISS 是贯穿全程的取舍原则。MVP 是 KISS 在验证阶段的具体形态。
- 与 `mm-de-risking` 的区别: 去风险化关心"怎么用最小成本消除最大不确定性"，是目的；KISS 关心"怎么让方案本身变轻"，是手段。两者常配对使用。

## E — 可执行步骤 (Execution)

1. **列出当前方案的全部组成要素**
   - 完成标准: 把方案拆成 5-15 条可独立删除的条目（步骤、模块、条件、会议、文档、分支）。
2. **逐条问："删掉它，结论/效果会变吗？"**
   - 完成标准: 每条标注"删了会崩 / 删了有风险但可观察 / 删了无所谓"。标为"无所谓"的直接删；标为"有风险"的进入第 3 步。
   - 判停条件: 若某条被多人指为"以防万一"但说不出触发场景，直接删除，不必讨论。
3. **给剩下"有风险"的条目各配一个最低成本验证**
   - 完成标准: 为每条写出一个能在最短时间内、用最小代价完成的检验动作（一次电话、一个假页面、一页纸推演），而不是把该条目原样保留。
4. **输出简化后的方案 + 一句核心假设**
   - 完成标准: 方案能用不超过 3 句话说清，并明确写出"这一版要验证的核心假设是什么"，以及下一步拿到反馈后的调整方向。

## B — 边界 (Boundary) ★

### 不要在以下情况使用
- **复杂性已被证明必需**：安全、合规、并发、灾备等领域，"以防万一"正是职责所在，删掉就是事故。
- **需要精度而非速度的场合**：科学建模、医疗诊断、金融风控里，简单模型的偏差代价可能远高于复杂模型。

### 容易误用的地方
- **书中未给边界**。以下是基于机制推导的警告：
- （推导, 非书中明示）**把简化当成跳过验证**：KISS 的完整动作是"简化 + 低成本验证"两步，只做第一步会变成草率。
- （推导, 非书中明示）**把简单等同于粗糙**：删掉的是"不影响结论的部分"，不是质量、不是必要的说明。
- （推导, 非书中明示）**用它压过提出复杂方案的人**：正确用法是逐条追问"删掉它会怎样"，不是整体宣布"太复杂了"。
